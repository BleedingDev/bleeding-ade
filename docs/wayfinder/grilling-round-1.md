# Grilling round 1 — the job and the hard boundary

This round resolves **Define the job BleedingADE must be hired to do**. Answer from real recent work, not feature taste.

## 1. Three painful sessions

Describe three real coding-agent sessions where your current setup lost time, context, control, or confidence.

For each, include:

- project and task;
- machine and device used to supervise it;
- runtime/provider and approximate agent count;
- what happened;
- what you needed to know or do but could not do quickly;
- the concrete cost or risk.

## 2. The indispensable job

Complete:

> When **_____**, I need BleedingADE to **_____**, so that **_____**.

Then answer:

- What would make you open BleedingADE every day instead of T3 Code, Herdr, AgentBox, Beads, or a provider CLI directly?
- What is the smallest result that would make the product genuinely irreplaceable rather than merely convenient?

## 3. Rank the outcomes

Rank the five most valuable outcomes and explain the top two:

- continue and steer work from phone;
- understand many agents at a glance;
- never lose running work or context;
- coordinate task dependencies and ownership;
- answer approvals/questions globally;
- reconnect from any device;
- move execution between machines;
- search/replay historical work;
- compare or switch runtimes easily;
- trust that UI state is accurate.

## 4. Define “same session”

Which of these must remain literally the same across devices?

- OS process;
- provider conversation/session ID;
- transcript and tool history;
- worktree and uncommitted files;
- installed environment and running services;
- agent tree/workflow state;
- control ownership.

For v1, is reconnecting every client to the original machine enough, or must execution genuinely move to another machine?

## 5. Phone authority

From a phone, which actions must be first-class?

- observe;
- prompt/steer;
- approve/deny;
- answer agent questions;
- interrupt/stop;
- start new work;
- transfer control;
- resolve conflicts;
- inspect diffs/artifacts;
- edit files directly.

## 6. Scale and trust

- Who is v1 for: only you, a trusted small team, or external users?
- Typical and maximum concurrent projects, execution machines, top-level agents, and child agents?
- May code enter third-party cloud boxes? May credentials?
- Rank the worst failures: lost work, leaked secret, stale/misleading UI, duplicate execution, unauthorized command, or unavailable session.

## 7. Ruthless proof

Name:

- three capabilities that must exist in the first integrated proof;
- three attractive capabilities that can disappear from v1 without regret;
- one scenario that, if BleedingADE cannot handle it, means the architecture is wrong.
